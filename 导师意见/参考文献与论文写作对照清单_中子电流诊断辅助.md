> 整理时间：2026-09-16  
> 目的：供论文撰写、Introduction/Related Work组织、方法定位、实验设计和论文层级提升参考。

## 1. 先明确本工作的研究主线

当前工作的核心并不是“用大语言模型直接给中子探测器做故障分类”，而是构建一条更适合真实核工程场景的、可追溯的诊断辅助链：

```text
unlabeled neutron-current time series
        ↓
deterministic / registered probes
        ↓
auditable observations
        ↓
structured alert summary
        ↓
authority-aware technical-document retrieval
        ↓
citation-bearing candidate interpretation
        ↓
engineering review
```

这条路线包含三个相互关联但应明确区分的问题：

1. **无标签工业时序如何变成可审计观测**：spike、zero event、co-movement、lag、extreme、snapshot等均由确定性工具产生，而不是由LLM自由解释。
2. **观测如何连接到技术证据**：将结构化观测转成技术检索意图，检索IAEA及同领域技术文档，形成带引用的候选解释。
3. **RAG本身是否可靠**：研究corpus expansion、query language、chunking、encoder与source priority之间的关系，而不是只比较cosine similarity。

因此，最接近本工作的文献并不集中在一个社区中，而是分布在：

- 核工程RAG与可信决策支持；
- LLM + 专业工具调用；
- 工业时序故障诊断；
- 人在回路诊断；
- RAG细粒度评价与鲁棒性；
- 安全关键工程系统的高水平故障诊断。

下面的文献应作为一个“组合参照系”来阅读，而不是寻找一篇完全同构的文章照着写。

## 2.1 RADIANT-LLM：核工程中最接近的直接参照

### 文献信息

**Ndum, Z. N., Tao, J., Ford, J., Yim, M., Liu, Y.**  
**A retrieval-augmented, domain-intelligent agentic framework for reliable decision support in safety-critical nuclear engineering**  
*Reliability Engineering & System Safety*, Volume 277, Part 2, Article 113057（卷期为2027年1月；文章已在线发表）  
DOI: 10.1016/j.ress.2026.113057

### 下载/全文链接

- 出版社页面：<https://www.sciencedirect.com/science/article/pii/S0951832026008665>
- arXiv预印本：<https://arxiv.org/abs/2604.22755>
- arXiv PDF：<https://arxiv.org/pdf/2604.22755>

### 为什么与本工作最接近

该工作属于：

```text
nuclear engineering
+ retrieval-augmented generation
+ agentic workflow
+ provenance / citation
+ safety-critical decision support
+ human validation
```

与本工作的共同点是：

- 都不适合把自由生成的LLM作为最终决策主体；
- 都强调technical evidence、traceability、citation和human review；
- 都考虑核工程技术文档中的表格、图、公式和领域术语；
- 都把RAG可靠性而非语言流畅性作为工程可信度核心。

### 与本工作的关键区别

RADIANT-LLM主要解决：

```text
documents → evidence-grounded answers
```

本工作进一步增加了measurement side：

```text
raw neutron signal
→ deterministic observations
→ structured condition description
→ technical evidence retrieval
→ engineering memo
```

因此，在Introduction中非常适合把RADIANT-LLM作为最近邻工作，然后明确指出：

> 现有核工程RAG工作主要从技术文档出发提供证据支撑，而真实在线监测任务还存在一个上游问题：如何在缺少统一故障标签的情况下，将海量原始传感器时序转换为可审计、可用于技术检索的观测语义层。

### 学生重点学习

1. Introduction如何把“LLM+RAG”写成**safety-critical decision support**问题；
2. 如何强调provenance、citation、hallucination与human validation；
3. 如何避免“做了一个聊天机器人”的低层次叙事；
4. 核工程论文中如何定义自动化边界与工程责任边界。

## 2.3 AgentMD：学习“LLM选择工具，而不是拥有计算权”

### 文献信息

**Jin, Q., Wang, Z., Yang, Y., et al.**  
**AgentMD: Empowering language agents for risk prediction with large-scale clinical tool learning**  
*Nature Communications*, 16, 9377 (2025)  
DOI: 10.1038/s41467-025-64430-x

### 下载/全文链接

- Nature官方页面：<https://www.nature.com/articles/s41467-025-64430-x>
- PMC免费全文：<https://pmc.ncbi.nlm.nih.gov/articles/PMC12549800/>

### 与本工作的对应关系

AgentMD构建并质量检查大量临床计算器，然后由language agent选择和调用相应工具。

其研究哲学与本工作中的：

```text

```

### 学生重点学习

1. 如何把“LLM调用Python函数”提升为**tool-using language agent**研究；
2. 为什么专业工具要有质量检查、unit tests和execution boundary；
3. 文章如何分别验证“tool builder”和“tool user”；
4. 顶刊文章如何用大规模工具集和真实病例证明工程意义。

### 对本稿的直接启发

目前文章中“registered probes + fail closed + active workspace + deterministic outputs”这一部分是有价值的，不能写成简单的实现细节。它应被明确表述为：

> **measurement authority is assigned to deterministic tools, while the language model is restricted to orchestration and evidence organization.**

这会比“我们用了一个ReAct agent”高一个层级。

# 7. 阅读这些论文时，重点不是“模仿题材”，而是回答下面五个问题

## 7.1 研究对象究竟是什么？

不要把论文写成：

> We use an LLM agent to analyse neutron-current CSV files.

更好的问题是：

> 大规模核仪表历史数据缺少统一样本级故障标签，但工程解释必须可追溯到原始测量和权威技术证据。如何构建一种既能规模化筛查无标签时序、又不越过工程判断边界的诊断辅助方法？

---

## 7.2 LLM和专业工具之间如何分工？

推荐坚持：

```text
LLM:
- select registered tools
- organize observations
- formulate/reformulate retrieval intent
- compose evidence-linked text

Deterministic tools:
- compute signal statistics
- detect events
- estimate lag/correlation/extrema
- own numerical measurement outputs

Runtime / workspace:
- own state
- own active record
- validate actions
- preserve provenance

Engineer:
- judge physical mechanism
- assess contextual adequacy
- make final engineering decision
```

这是本工作的一个真正优势。

---

## 7.3 论文创新不应写成“我们用了RAG”

RAG已经是成熟技术。

更值得强调的创新是：

### A. Measurement-to-evidence semantic interface

```text
raw measurement
→ deterministic observation
→ structured alert
→ retrieval intent
→ technical evidence
```

### B. Evidence hierarchy / source-policy问题

```text
high semantic similarity
≠
high authority / preferred evidence source
```

当前实验中最值得保留和强化的结果就是：

> 随着same-domain supplementary documents扩展，nearest-neighbor cosine可以提高，但预指定IAEA权威来源的Priority@10可能显著下降。

这说明安全关键RAG不能仅由similarity驱动。

### C. Retrieval robustness是系统耦合问题

```text
retrieval behaviour
= f(query formulation,
    language,
    encoder,
    chunking,
    corpus scope,
    source policy)
```

而不是简单的：

```text
retrieval quality = embedding model quality
```

## 8.2 Tool-augmented and human-in-the-loop diagnostic assistance

- ChatCAD

## 8.4 Gap to be addressed

最后自然收束到：

> 现有工作分别解决了工业时序诊断、专业工具调用和技术文档RAG，但对于**缺少统一故障标签的核仪表原始时序**，仍缺少一条从measurement-side auditable observation construction到authority-aware evidence retrieval的完整、可追溯流程；同时，面向核工程部署的retrieval source-policy robustness仍缺少系统研究。

这是目前比较适合本论文的研究缺口。

# 9. 对当前论文实验部分的启发

现阶段文章已经有一套不错的retrieval robustness实验：

```text
corpus expansion
query language
query formulation
chunking
encoder
cosine score
Priority@10
first-authority rank
strict recall / MRR
document-level recall / MRR
```

如果后续有条件再补工作，优先顺序建议是：

## 第一优先级：expert relevance annotation

抽取有限数量代表性query和retrieved passages，由核仪控专家标注：

```text
relevant / partially relevant / irrelevant
```

这样可回答：

> source priority下降究竟只是来源变化，还是实际技术相关性也发生变化？

## 第二优先级：claim–evidence support

从最终memo中抽取claim，让专家判断：

```text
fully supported
partially supported
unsupported
```

与ARES/RAGChecker的评价思想接轨。

## 第三优先级：observation correctness

选取有限数量典型record，对：

```text
spikes
zeros
lag
co-movement
regime
```

进行人工核查。

这样可以建立：

```text
raw data correctness
→ observation correctness
→ retrieval correctness
→ evidence support
```

的完整验证链。

## 第四优先级：expert usefulness

让工程人员评价condition report / evidence memo是否：

- 减少筛查时间；
- 有助于确定下一步检查；
- 是否存在误导性信息；
- 引用是否便于复核。

做到这一层，论文工程意义会明显增强。

# 10. 建议始终坚持的三个核心思想

## 10.1 Do not diagnose before you describe.

先回答“数据中发生了什么”，再讨论“为什么发生”。

```text
observation ≠ physical cause
```

---

## 10.2 Semantic relevance is not evidence authority.

```text
cosine similarity ↑
```

并不意味着：

```text
authoritative evidence visibility ↑
```

对于核工程，source policy、metadata、filter和reranking本身就是系统设计的一部分。

---

## 10.3 LLM should organize evidence, not manufacture evidence.

```text
measurement/calculation → deterministic tools
state/provenance → runtime
knowledge support → retrieved documents
final physical judgment → engineer
LLM → orchestration + organization + language interface
```

这是最适合当前工作的可信AI边界。

---

# 11. 一句话总结这组参考文献对本论文的意义

当前工作的潜在特色并不是“核工程里也用了一个LLM/RAG”，而是把多个社区分别发展的思想连成一条完整工程链：

```text
unlabeled neutron time series
→ deterministic auditable probes
→ structured observation
→ authority-aware retrieval
→ citation-backed diagnostic assistance
→ engineering review
```

目前高水平文献中可以分别找到**核工程RAG、专业工具调用、工业时序诊断、人在回路和RAG评价**的优秀参照，但很少看到上述五层在无标签核仪表时序问题中被完整连起来。

因此，论文撰写时应重点学习这些文献的**问题定义、责任边界、验证方法和叙事层级**，而不是把自己的工作改写成一个普通的LLM fault classifier。
