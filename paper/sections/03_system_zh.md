## 2.1 数据说明

本研究使用两类互补资源：用于 Agent 侧诊断的电厂中子电流测量数据，以及用于手册锚定 RAG 与检索评测的核仪控（I&C）手册语料。

### 中子电流测量档案

底层测量档案按四个多通道中子电流 CSV 组别组织（下文记为 A1、A2、B1、B2），对应同一电厂采集活动中的不同仪表组。档案共含 42 个序列文件，组成见表 1。

**表 1 中子电流测量档案组成**

| 组别 | 序列数 | 每序列通道数 | 每序列列数 |
|------|--------|--------------|------------|
| A1 | 11 | 7 | 8 |
| A2 | 11 | 7 | 8 |
| B1 | 10 | 7 | 8 |
| B2 | 10 | 7 | 8 |
| 合计 | 42 | — | — |

每个序列包含一列时间与七个中子电流通道（共八列）；通道标识遵循电厂标签约定（如 `RIC…MA_VER`）。组内七个探测器按圆形（环向）布置于反应堆周围，因此相邻通道对应相邻角向位置，而非 CSV 列序上的任意排列。代表性序列约有 \(6\times10^{5}\) 量级采样点，标称间隔 1 s，覆盖多日窗口。

需要强调：原始 CSV 的时间戳仅近似按时间排列，导出记录中存在局部乱序与非单调片段，并非严格递增。因此 Agent 在任何下游探针之前，都会先做显式的时间排序。

该采集活动的部分记录确实存在电厂侧运行注释与故障相关信息；但这些标注来源不一、形态异构，尚未整理成可直接制表的、样本级统一故障分类体系。故本文不报告故障标签数量。零先验 Agent 将通道标签视为不透明标识，分析过程不消费故障标签；既有标注留待未来监督基准，而非当前流水线输入。

系统演示与结果章案例取自 A1、A2 组中的工作子集，在各自工作区内独立处理；同一 Agent 协议可原样用于档案中其余序列。

### 核仪控手册语料

知识语料共 59 份技术文档（由 PDF 转为 Markdown 后建索引），划分为核心库（core）与非核心补充库（non-core）。核心库为 13 份 IAEA 手册，包括仪表通道在线监测（OLM）以及过程/部件状态监测与诊断报告，以及其他 IAEA 关于仪控设计、数字化改造、维修/监督、运行限值与规程等指南。非核心库为其余 46 份同域手册，来自 NRC、EPRI/DOE、OECD/NEA 以及传感器、噪声、堆芯/仪表监测等相关实验室或专题材料。

这些非核心文档不只是应被拒绝的噪声，而是主题相关的补充知识，用于在受控条件下扩大可检索知识库。本文的一个核心实验问题因此是核心库—非核心库关系：当核心与非核心文档配比变化时，检索行为如何变化——换言之，在固定核心库规模下，可以接入多大的非核心补充，而不至于稀释对核心证据的检索。该受控扩张支撑评测章中的语料范围外推与自检索实验。

## 2.2 零先验诊断 Agent

### 2.2.1 设计目标

测量侧目标是：在不依赖故障标签库、固定通道—物理映射或手工频带的前提下，将原始中子电流 CSV 转为结构化、可读的工况报告。通道标签视为不透明标识；统计形态、冗余、异常与时空线索由序列本身发现。这一“零先验”立场与 2.1 中标注异构、推理时不消费故障标签的设定一致。

### 2.2.2 架构与控制环

Agent 将本地大语言模型（LLM）规划器与确定性工具路由相结合。规划器提出工具调用；Python 路由执行已注册的分析器，并返回简洁状态信息，用于更新持久化工作区黑板（`state.json`）。仅入口探针可以接收原始文件路径；之后每个探针只能接收工作区目录，并从黑板解析当前激活的 CSV。工作流见图（Agent 工作流图）。

初始化之后，规划器不得再复述自由文本文件路径。LLM 工具调用仍然脆弱：模型可能虚构不存在的 API、给出错误参数，或生成流畅但不忠实的内容。因此工作区合约把权威路径与可信任状态留在运行时一侧，规划器只选择下一步已注册探针；推动这些约束的失败模式见 2.2.5。

### 2.2.3 工作区初始化

给定 CSV 路径后，装载与剖析探针创建专用工作区目录，解析时间列，将序列按时间递增排序（以应对 2.1 所述原始非单调导出），并写入清洗后的激活文件。同时在黑板上记录基本健康指标（规模、标称采样间隔、缺失情况、不活跃通道），并向工况报告追加初始化段落。若黑板缺失，后续探针拒绝运行，从而强制完成必要的预热步骤。

### 2.2.4 统计发现与异常探针

初始化后，规划器可调用表 2 所列探针。零先验发现探针进行全局纵向扫描：用唯一值数量与变异系数划分粗粒度形态角色（离散/阶跃型、高惯性、高波动或常规连续），并用成对相关发现近冗余通道对（\(|r|\ge 0.99\)）以及强共动组。结合圆形探测器布置，此类共线往往指示角向相邻或功能冗余传感器，而非偶然数值吻合。

异常/工况探针继而对各通道进行稳态/暂态分段，枚举尖峰事件与孤立零值闪断，并汇总哪些通道主导各类异常。时滞扫描计算通道间互相关，以区分超前—滞后传导链路与基本同步的群组。极值扫描定位全局极大/极小值及其时间戳；空间快照探针在选定时刻冻结多通道横截面，便于在识别极值后使用。这些探针共同积累可表述为尖峰、掉零、冗余与工况切换的证据，且无需监督类别标签。

**表 2 中子电流 Agent 所用诊断探针（末列实现标识仅供复现）**

| 探针 | 说明 | 实现标识 |
|------|------|----------|
| 装载与剖析 | 创建工作区、排序时间戳、记录数据健康指标 | load_and_profile_csv_tool |
| 零先验发现 | 推断形态角色，发现共动或近冗余组 | zero_prior_discovery_tool |
| 异常/工况 | 分段工况；枚举尖峰与零值闪断 | anomaly_detector |
| 时滞扫描 | 估计超前—滞后相对同步群 | global_time_lag_scan_tool |
| 极值扫描 | 定位全局极大/极小值及时间戳 | global_extremes_scan_tool |
| 空间快照 | 选定时刻的多通道横截面 | get_spatial_snapshot_tool |

### 2.2.5 设计过程与采用的约束

2.2 节所述架构是失败驱动、迭代收敛的结果，而非一次性先验规格。早期原型几乎把全部簿记交给规划器：每次探针调用都复述绝对 CSV 路径、工具回复被要求近乎纯 JSON，工况文本又几乎原样送入下游诊断。在本地中等规模 LLM 上，多步中子电流分析反复暴露这些问题。下表概括最终作为硬约束保留的条目；本小节其余段落按机制展开各行所对应的失败与对策。

**表：设计问题与最终测量侧协议采用的约束**

| 设计问题 | 采用的约束 |
|----------|------------|
| 多步复述路径出错（错文件夹；原始 vs 排序副本） | 仅装载—剖析接受 CSV 路径；后续探针只传工作区目录，从黑板解析激活文件 |
| 本地 LLM 导致 JSON 丢失/残缺 | 去 Markdown 围栏；抽取首个括号平衡 JSON；仅接受已注册探针标识 |
| 工况文本过长拖垮下游推理 | 保留人类可读报告；RAG 由紧凑结构化告警摘要驱动 |
| 无手册依据的诊断空话 | 由结构化摘要构造查询；要求多阶段、带引用的仪控语料检索 |

若每一步都用自由文本重发路径，转录错误会沿探针链累积：规划器混淆工况文件夹、把原始导出与时间排序副本混用，或让后续探针指向与刚剖析不同的序列。运行时若信任路径参数，此类错误会静默执行并产出自相矛盾的报告，而非显式拒绝。采用的补救是：仅装载—剖析步骤接受路径；它创建专用工作区、写入清洗后的激活文件，并把权威位置记入黑板；此后探针只接受工作区目录，再从黑板解析序列。路径所有权从易变的模型字符串转移到运行时契约；黑板缺失时未完成预热也会失败关闭。

第二类失败出现在动作接口。严格的「仅 JSON」提示很脆弱：本地模型常把工具调用包进 Markdown 围栏、夹杂简短自然语言，或截断花括号，路由器因而丢弃本可执行的动作；完全放开自由文本又使解析同样不可靠。现抽取器因此先去围栏，再搜索首个括号平衡的 JSON 对象/数组，并在执行前校验 `action` 是否为已注册探针标识；虚构分析器名称失败关闭。这并不宣称结构化生成完美，而是把本地模型的不完美输出当作默认情形，只要存在结构良好的对象就尽量恢复调用。

即便探针链跑完，未经裁剪的多页工况叙述也会拖垮手册诊断阶段：模型须同时消化冗长散文并挑选手册段落，容易产出含糊、依据薄弱的摘要。设计因此区分受众：工作区保留按时间顺序的人类可读报告供核查；紧凑结构化摘要（分变量告警、尖峰/零值计数、共线或滞后线索）则作为通往 RAG 的机器接口。检索查询由该摘要派生，而非由操作员对适用手册条款的自由文本猜测驱动，合成器须为检索块附加编号引用。本文保留的示例工作区中，代表性 A1/A2 序列可见完整探针链，另有序列出现部分完成或同一探针的冗余重调；这表明工作区与 JSON 契约可强制执行，但规划纪律仍影响覆盖——此为说明性观察，用以支撑协议设计，而非带虚构恢复率的监督准确率声明。

### 2.2.6 调用协议与输出

工具调用须以约束 JSON 对象给出（`{"action": …, "parameters": …}`），可置于 Markdown 围栏中；运行时即使 LLM 附加说明文字，也会抽取首个平衡的 JSON 对象或数组，以缓解前述 JSON 丢失问题。本地路由仅接受表 2 中已注册的探针标识（本文部署为 Ollama qwen2.5:7b），虚构的分析器名称将失败关闭，而不会执行未定义路径。每次成功调用会向工作区报告追加叙述块，并更新黑板上的结构化字段（如形态角色、尖峰/零值摘要、滞后组）。由此得到的工况报告（连同可选 JSON 快照）构成通往 RAG 阶段的唯一测量侧接口：下游检索由观测现象驱动，而非由操作员对适用手册条款的自由文本猜测驱动。

## 2.4 报告驱动的多阶段 RAG 诊断

工况报告被解析为紧凑 JSON（分变量告警、尖峰摘要、拓扑/共线线索）。查询由该 JSON 构造，而非仅依赖简短自由文本。检索分阶段进行（现象/机理段落，再补充冗余/拓扑相关段落），LLM 据此生成带编号引用（`[n]`、`Rn`）并与检索块关联的多部分诊断。由于诊断质量依赖检索，评测章单独评估该知识层。
