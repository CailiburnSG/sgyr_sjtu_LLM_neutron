# 参考 ChatCAD 的研究流程草案

> 本文档记录一条可借鉴 ChatCAD 的研究流程。核心问题应表述为：如何将多通道记录中的可验证观测，转换为受证据约束、可回查的仪表分析报告？

不要将目标表述为“LLM 诊断核设施故障”。在缺少真实故障标签和专家复核时，系统的结论边界应保持在可观察现象、候选解释与待核查事项。

## 1. 总体流程

```text
独立原始记录
  → 专业分析模块：提取可观测现象
  → 标准化事件卡：时间、通道、幅度、持续时间、统计证据
  → 技术资料中的受控证据片段
  → LLM：只整合卡片与证据，输出受限分析报告
  → 与真值、标注或受控试验对照评价
```

这对应 ChatCAD 的基本分工：专业模型先产生结构化发现，LLM 负责整合、说明和交互，而不直接替代专业分析模块。

## 2. 定义可验证的专业发现任务

这一步对应 ChatCAD 中定义的五种胸片病征。任务不应是“真实故障原因”，而应限定为可以从数据中客观定义的观测类别，例如：

- 连续零值或掉线段；
- 孤立尖峰；
- 饱和或截断；
- 缓慢漂移或偏置；
- 通道间不一致；
- 时间同步偏移；
- 多通道同步变化与局部变化。

每个事件应使用固定字段：

```text
事件类别｜起止时间｜涉及通道｜幅度或持续时长｜
与基线的差异｜跨通道关系｜算法证据｜
可引用的技术资料片段｜不确定性
```

这些标签应称为“观测现象”，而非直接称作“探测器故障”或“堆芯异常”等物理诊断。

## 3. 所需数据

至少需要四类数据：

| 数据 | 用途 | 当前情况 |
|---|---|---|
| 原始多通道记录 | 分析模块输入、案例来源 | 已有 |
| 记录元数据 | 通道名、采样率、时间、运行状态、数据来源 | 需核对是否齐全 |
| 技术资料库 | 解释边界、来源追溯 | 已有 |
| 事件真值集 | 定量评价依据 | 当前最缺 |

### 事件真值的可能来源

1. **运行、维护或报警记录与原始数据对齐**：最强，但目前可能缺失。
2. **小规模人工标注集**：不必先判断真实机理；仅标注连续零值、发生通道、时间范围等可观察事实。即使只有 100–200 个独立事件，也能形成比无真值更可靠的评价基础。
3. **留出稳定原始片段后的受控注入**：只在测试集注入连续零值、尖峰、漂移、通道偏置、时间错位等已知扰动。它可严格评价数据层异常观测与定位，但不能证明真实工程故障诊断能力。

若缺少前两类真值，论文应表述为“测量记录完整性或一致性分析”，而不是设备诊断。

## 4. 专业分析模块

该模块对应 ChatCAD 中的专用视觉/报告网络。未必需要重新训练机器学习模型；可使用已有的确定性分析功能，例如：

- 零值段检测；
- 尖峰与异常幅度检测；
- 滞后或同步关系计算；
- 通道间差分、相关性和稳定性指标；
- 窗口级统计特征与趋势检测。

模块输出不应是一段自由文字，而应是机器可读的事件卡 JSON，例如：

```json
{
  "event_type": "continuous_zero_segment",
  "channels": ["I3"],
  "start_time": "...",
  "duration_s": 18.4,
  "baseline_mean": 2.31,
  "observed_mean": 0.00,
  "cross_channel_consistency": "inconsistent",
  "evidence": ["zero_ratio=1.0", "other channels remain nonzero"]
}
```

若要使用同门的模型结果，应先明确合作、署名与工作边界；否则优先采用独立的规则和统计模块。

## 5. LLM 的受限职责

LLM 不重新判读原始波形，而只做三件事：

1. 将多个事件卡合成规范、简洁的分析报告；
2. 将观测现象连接到技术资料中的具体证据片段；
3. 明确区分观察到的事实、资料支持的可能解释和待核查事项。

输出应强制使用 JSON 或固定章节，并要求每一个“可能解释”附带文献定位：

```text
观察到的事实：由事件卡直接支持
可能解释：由资料支持，但不是确认诊断
待核查事项：系统不能从现有数据断言的内容
```

LLM 的作用应是受约束整合与可读表达，而不是自由推理。

### 5.1 embedding 的位置：证据检索基础设施，而非论文主任务

embedding 仍然保留，但从“要证明排序有多准确的算法”变为证据层的候选召回器：

```text
事件卡中的可检索描述
  → embedding / BM25 召回候选技术资料片段
  → 元数据或资料类别过滤
  → 少量可回查证据片段
  → LLM 只能基于事件卡与这些片段生成说明
```

embedding 的可保留用途：

1. 从中英文技术资料库召回与观测现象相关的候选段落；
2. 为每条 LLM 解释提供可定位的原文来源；
3. 可选地检索历史相似事件卡，作为“相似观测案例”，但不得把相似案例直接当作真实机理诊断。

应保留文档切块、索引、来源元数据与原文定位能力。查询应由事件卡字段生成，并可按资料类别过滤。可采用多语种检索模型（例如 bge-m3）重建索引，但更换 embedding 模型不是主要贡献。

以下内容不再作为论文核心：余弦相似度、Top-k、MRR、Recall@k、自检索、随机扩库和 embedding 模型排名比较。新的评价对象是“引用是否可定位、是否支撑对应说明”，而不是“预先指定的资料是否被排在前面”。

### 5.2 LLM 的输入包与输出约束

每个 LLM 请求应使用固定的证据包，而不是把原始 CSV 或无边界的长文本直接交给模型：

```text
输入包 = 事件卡 JSON + 必要的波形/统计摘要 + 最多 K 条已定位资料片段 + 固定任务指令
```

输出必须满足固定结构，并可被程序解析：

```text
1. 已观测事实：只能复述事件卡字段；
2. 数据证据：引用事件卡中的数值或统计量；
3. 可能解释：每项必须绑定资料片段编号；
4. 待核查事项：明确系统不能确认的内容；
5. 引用来源：文件、章节或段落定位。
```

约束规则：

- 不得修改事件类型、通道、时间范围或数值；
- 不得将相关性或时间领先关系表述为因果；
- 没有来源时只能写“无法确认”，不得补充机制性判断；
- 可能解释必须使用不确定措辞，不能替代人工工程诊断；
- 输出优先使用 JSON 或严格固定章节，以便自动核验字段。

### 5.3 模型比较的目的与最小组合

不同 LLM 应被视为可替换的报告组件。模型比较的目的不是堆砌模型名称，而是检验流程是否依赖单一模型、模型规模是否影响忠实性与越界风险，以及本地部署是否可行。

最小模型组合可为：

| 版本 | 作用 |
|---|---|
| 模板报告（无 LLM） | 非 LLM 基线，直接以事件卡字段填充报告 |
| Qwen2.5-7B-Instruct（本地） | 中文资料和中文报告的主模型 |
| Qwen2.5-14B-Instruct（本地） | 同一模型族的规模对照；资源不足时可省略 |
| Llama 3.1 8B-Instruct（本地） | 不同模型族的通用性对照；资源不足时可省略 |

所有模型必须接收完全相同的事件卡、资料片段、提示词和输出格式要求。若计算资源有限，至少保留“模板 + 一个本地 LLM”；若要提出流程具有跨模型适用性，则至少比较两个 LLM。

## 6. 实验设计

### A. 专业发现任务的正确性

在人工标注集或受控注入集上评价：

- 事件检测：Precision、Recall、F1；
- 时间定位：区间 IoU、起始时间误差、检测延迟；
- 通道定位：macro-F1；
- 不同扰动强度、持续时间和噪声条件下的鲁棒性。

这是最硬的量化结果。

### B. LLM 是否忠实保留专业发现

将 LLM 报告重新解析为事件字段，并与输入事件卡对照：

- 事件类型、通道、时间范围、严重度的字段 F1；
- 数值篡改率；
- 关键字段遗漏率；
- 不被事件卡支持的断言比例。

这对应 ChatCAD 从生成报告抽取疾病标签，再与真值比较的基本逻辑。

### C. 技术资料是否支撑说明

这部分不应称为“检索准确率”，而是“证据支撑质量”：

- 引用是否能定位到真实段落；
- 引用片段是否确实支持该条解释；
- 系统作出的解释中，有多少附有来源；
- 有多少解释超出了来源或事件卡。

最好抽样 50–100 个“事件—说明—引用”三元组，由两名具备基本专业背景的评阅者标记“支持 / 不支持 / 无法判断”。若完全找不到专家，只能评价来源可定位和字段一致，不能宣称解释正确。

### D. LLM 忠实性、安全性与跨模型比较

在完全相同的事件卡和证据包下，比较模板、不同 LLM 或不同提示约束：

- **字段忠实率**：事件类型、通道、时间范围、严重度和数值是否与事件卡一致；
- **关键字段遗漏率**；
- **数值篡改率**；
- **无证据断言率**：既不由事件卡支持、也没有资料来源的机制性说法比例；
- **引用可定位率**；
- **引用支撑率**：引用段落是否支持对应解释；
- **输出格式合规率**与推理耗时。

字段忠实率、遗漏率、数值篡改率和格式合规率可自动计算；引用支撑率与无证据断言率需要抽样人工核查。结果不应预设为大模型一定更好：更大的模型可能降低字段遗漏，也可能生成更流畅但缺乏来源支持的说明。

### E. 消融与对照

| 版本 | 用途 |
|---|---|
| 仅专业分析模块 | 基线：提供事件卡，不生成说明 |
| 事件卡 + LLM，无技术资料 | 检查 LLM 自由发挥的风险 |
| 文档检索 + LLM，无事件卡 | 对比“只会说知识”的系统 |
| 事件卡 + 文档证据 + LLM | 完整方案 |
| 不同 LLM / 不同提示约束 | 比较模型与约束机制 |
| 仅 dense retrieval / 混合检索 + 过滤 | 仅作为证据供给消融，不能将排序分数当主结论 |

关键不是证明“LLM 写得更顺”，而是验证：结构化专业输入与证据约束能否让输出更完整、更忠实、更少越界。

## 7. 结论边界

若按此路线推进，最终工作更接近“专业分析模块 + 受约束 LLM 报告”的系统论文。其可信度取决于能否建立一小套可信的事件真值或人工审查集。

没有该评价基础时，系统最多形成案例展示，难以构成可证伪的研究实验。
