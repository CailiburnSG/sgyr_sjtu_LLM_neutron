# 事件卡生成与聚合设计草案

> 目标：不直接人工挑选事件卡，而是由函数从现有快照或原始 CSV 中产生可复核的原子观测，再按公开规则聚合为标准事件卡。

## 1. 两层数据结构

```text
快照或原始数据
  → 原子观测（单个通道的一次零值、一次尖峰等）
  → 聚合函数
  → 多通道事件卡
```

### 原子观测

原子观测是“一个通道在一个时刻或区间出现一次可定义现象”。例如：

```json
{
  "record_id": "A1_1",
  "event_type": "short_zero",
  "channel": "BL...RIC1011MA_VER",
  "time": "2025-01-21 01:04:59",
  "source": "A1_1...数据快照.json"
}
```

### 聚合事件卡

聚合事件卡将时间接近、现象相同、跨通道有关联的原子观测合并。例如：

```json
{
  "event_id": "A1_1_short_zero_20250121_010459",
  "record_id": "A1_1",
  "event_type": "short_zero",
  "time_start": "2025-01-21 01:04:59",
  "time_end": "2025-01-21 01:04:59",
  "channels": [
    "BL...RIC1011MA_VER",
    "BL...RIC1012MA_VER",
    "BL...RIC1013MA_VER"
  ],
  "channel_count": 3,
  "scope": "multi_channel_temporal_cluster",
  "evidence": {
    "source_snapshot": "A1_1...数据快照.json",
    "atomic_observation_count": 3,
    "merge_window_seconds": 1
  }
}
```

若事件簇只有一个通道，`scope` 为 `single_channel`。

## 2. 从当前快照读取

当前快照中的每个变量包含：

```json
{
  "var_name": "...",
  "alerts": {
    "isolated_zeros": ["01-21 01:04:59", "..."],
    "spikes_summary": {
      "total_count": 10,
      "top_peaks": {},
      "duration_range_sec": [1, 14]
    }
  }
}
```

### 可直接生成的卡：孤立零值

读取历史 JSON 后，对每个 `var_name` 的 `isolated_zeros` 中每一个时间创建一条 `short_zero` 原子观测。随后按记录、事件类型和时间接近程度聚合；正式路径仍以原始 CSV 为准。

### 当前快照不能直接严格生成的卡：尖峰

当前 JSON 仅保存尖峰总次数、峰值汇总和持续时间范围，未保存每次尖峰的精确时间。因此不能只依靠 JSON 生成严格的尖峰事件卡。

试点阶段可从同目录的 `进阶全局工况报告.txt` 中读取单次尖峰时间与持续时间。正式实验应改造现有检测函数，让其直接写出结构化尖峰原子观测：

```json
{
  "event_type": "positive_spike",
  "channel": "...",
  "start_time": "2025-01-21 01:04:59",
  "end_time": "2025-01-21 01:05:01",
  "peak_time": "2025-01-21 01:05:00",
  "peak_value": 316.9,
  "duration_s": 3,
  "detector": "rolling_median_mad"
}
```

## 3. 聚合规则

对同一条记录、同一事件类型的原子观测：

1. 按时间排序；
2. 若相邻观测的时间差不超过合并窗口 \(\delta\)，归入同一事件簇；
3. 合并事件簇内的通道集合、起止时间和统计证据；
4. 根据通道数量和时间离散度标为单通道或多通道同步事件。

第一版可使用 \(\delta=1\) 秒，因为当前快照为秒级时间。后续应以 \(\delta=0,1,2\) 秒进行敏感性检查。

```text
同一 record_id
且同一 event_type
且时间差 ≤ δ 秒
  → 归为同一事件簇
```

零值与尖峰不应互相合并；不同类型先独立生成事件卡。通道相关、滞后关系等更复杂现象可在后续作为单独事件类型加入。

## 4. 快照与完整 CSV 的职责

| 阶段 | 数据来源 | 用途 |
|---|---|---|
| 试点 | 现有 JSON 快照 + 详细 txt 报告 | 直接生成约 20 张事件卡 |
| 正式实验 | 完整 CSV | 统一产出原子观测，并补充更多事件类型与精确数值 |
| 全流程 | 原始 CSV | 抽样回查事件卡，验证快照与解析未出错 |

完整数据无需一次性人工浏览。其主要作用是让同一检测函数批量、统一地生成事件卡，并在样本量扩展时提供更多独立记录。

## 5. 时间戳要求

当前快照中的时间格式如 `01-21 01:04:59` 缺少年份。试点阶段可用 `record_id + 局部时间` 保证唯一；正式版本必须保存完整 ISO 时间戳，例如 `2025-01-21 01:04:59`。

## 6. 论文中应报告的内容

论文方法部分应报告：

- 原子观测类型及定义；
- 事件聚合条件与合并窗口 \(\delta\)；
- 事件卡字段；
- 检测阈值及其确定方式；
- 对关键阈值和 \(\delta\) 的敏感性检查。

不需要写 JSON 解析、目录遍历、文本正则或具体循环实现。这些属于工程实现，可在附录、伪代码或代码仓库中提供。
