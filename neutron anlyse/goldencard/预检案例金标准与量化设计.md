# 预检案例金标准与量化设计

## 1. 任务单位

本研究的目标是对一段中子电流数据进行预检，而不是对每一张孤立事件卡作故障诊断。
因此，金标准的单位是**预检案例**：一个时间窗口中的事件组合，关联到最多三条证据卡和至多一项
固定检查行为。

```text
事件卡：观察原子
事件组合：预检案例输入 X
证据卡：Y
固定检查行为：Z
```

核心预测关系为：

```text
X → Y → Z
```

它表示“该预检案例选择哪些证据，以及这些证据支撑哪些检查行为”，不表示故障原因确认。

## 2. 预检案例构造

先在事件时间线上构造自然窗口：当相邻事件的时间间隔不超过冻结阈值 `τ` 时，将其归入同一
预检案例。`τ` 应在检查实际事件间隔分布后确定，例如候选的 5 或 10 分钟；确定后不得因
标注结果而改变。

无事件窗口也可保留为对照案例，用于评价无依据行动的误报。

每个案例用组合摘要而不是事件 ID 作为模型输入：

```json
{
  "precheck_input": {
    "window_duration_seconds": 600,
    "event_summary": [
      {
        "event_type": "short_zero",
        "count": 12,
        "duration_seconds": {"min": 0, "median": 1, "max": 4},
        "channel_count_range": [2, 7],
        "scope_counts": {"multi_channel_temporal_cluster": 12}
      },
      {
        "event_type": "positive_spike",
        "count": 5,
        "duration_seconds": {"min": 0, "median": 0, "max": 2},
        "channel_count_range": [1, 3]
      }
    ],
    "pattern_summary": {
      "temporal_recurrence": "repeated",
      "cross_channel_pattern": "multi_channel_cluster",
      "anomaly_density": "high"
    }
  },
  "trace": {
    "source_event_ids": ["..."]
  }
}
```

`trace.source_event_ids` 仅供审计回溯，绝不输入模型。事件卡本体无需为此修改。

案例目标数量可暂定为 80，但它是 80 个预检案例而不是“8 类事件各 10 张”。抽样时优先覆盖：

- 零值主导、尖峰/跌落主导与混合异常；
- 单通道局部异常与多通道同期异常；
- 短时高密度重复、长时间持续/重复与无异常对照窗口。

不应为了凑足类别而复制或制造同质单事件案例。

## 3. 金标准卡

一张案例卡的基本结构如下：

```json
{
  "goldcard_id": "GC-...",
  "precheck_input": {"...": "事件组合摘要"},
  "trace": {"source_event_ids": ["..."]},
  "evidence": [
    {
      "evidence_id": "E1",
      "content": "证据卡正文",
      "action_support_scores": {
        "signal_transmission_path_check": 2
      }
    }
  ],
  "gold_action_links": [
    {
      "action_id": "signal_transmission_path_check",
      "evidence_ids": ["E1"]
    }
  ]
}
```

每张案例最多保留三条最终证据。证据卡仍以 `evidence_id` 回指已有 300 张人工证据卡；其正文
可嵌入案例卡以方便标注与模型输入。

## 4. 支撑评分

评分对象不是“证据是否好”，而是：

```text
预检案例 X × 证据 Y × 固定检查行为 Z
```

采用有锚点的 0–2 整数分：

| 分数 | 定义 |
| --- | --- |
| 0 | 证据与该案例或该检查行为没有实质支撑关系。 |
| 1 | 证据与现象或主题相关，但不足以支持在该案例中正式建议该检查。 |
| 2 | 证据明确提供与案例相符的条件、对象或核查方向，可正式支撑该检查。 |

只有 `action_support_score = 2` 的证据才可写入相应的 `gold_action_links`。分数为 1 的
证据可作为条件性背景保留，但不作为正式依据。

证据不必逐字出现内部 `action_id`，但必须明确给出相关的条件、核查对象或检查方向。模型不得
用主题相似或自由推理把无直接依据的资料升级为正式支撑。若资料库没有足够证据，应如实标为
`evidence_gap`；若工程上仍需执行某项规范性核查，应另标为 `policy_based_check`，不得伪装为
`evidence_supported_check`。

### 单建议约束（v1）

第一版中，每个预检案例最多输出一项固定检查行为。该约束避免模型将四项核查泛化为异常后的
无差别检查清单，并迫使标注者与模型选择**最优先且证据最直接**的一项。若没有任何关系达到
2 分，输出 `evidence_gap`，即不输出固定检查行为；它不是第五种检查建议。

## 5. 标注与复核

标注者面对的是：预检案例 X、冻结的 300 张证据卡、四个固定检查行为定义。标注者从全库中
选出最多三条证据，并为其与检查行为的关系给 0–2 分。

为提高可复核性：

1. 先以 10–15 个案例做双人试标，并完善评分手册与正反例；
2. 正式标注由两名标注者独立完成，不显示模型输出、检索排名或模型分数；
3. 使用加权 Cohen's kappa 报告 0–2 支撑评分的一致性；
4. 分歧由第三人或共同仲裁，保留两份原始评分与仲裁结果。

## 6. 单次 LLM 推理

当前证据库只有 300 张人工证据卡，正文、ID、标签及结构化提示合计约 2.9 万 token，可在
64k 或更长上下文的模型中一次提供。因此主流程采用单次联合选择：

```text
输入：X + ALL-Y（全部 300 张证据卡）+ 固定行动定义
输出：最终 Y（最多三条）+ Y 对 Z 的 0/1/2 分数 + 0 或 1 项 Z
```

LLM 的输出必须是严格 JSON，并受以下约束：

- 只能选择输入证据目录中存在的 `evidence_id`；
- 最多选择三条证据；
- 只能使用既定的四个 `action_id`；
- 最多输出一个 `action_id`；若无直接支撑则输出 `evidence_gap`；
- 只有分数为 2 的证据可进入行动链接；
- 不输出具体故障原因或确认性因果结论；
- 全部证据卡按固定 `evidence_id` 顺序输入，避免顺序偏差。

未来资料库规模扩大到无法放入上下文时，才在该接口之前增加候选检索器；金标准结构和 LLM
输出结构无需改变。

## 7. 量化指标

主要评价分三层：

| 层次 | 预测对象 | 指标 |
| --- | --- | --- |
| 证据选择 | 最多三条 `evidence_id` | Precision@3、Recall@3、F1@3、Exact Set Match |
| 行动选择 | 单个 `action_id` 或 `evidence_gap` | macro-F1、准确率、`evidence_gap` 的 precision/recall |
| 核心任务 | `(evidence_id, action_id)` 且支撑分为 2 | 三元组 Precision、Recall、F1 |

补充安全指标：

- 无效证据 ID 率（应为 0）；
- 无依据行动率：输出行动却没有分数为 2 的引用证据；
- 无异常对照窗口上的行动误报率；
- 人工标注的加权 Cohen's kappa。

本文不将该任务称为“故障诊断准确率”，而称为：

```text
evidence-grounded precheck action selection
证据约束的预检行动选择
```

## 8. 开发与测试隔离

若第一阶段不微调模型，推荐将案例分为：

```text
20 个开发案例：确定提示词、JSON 输出和评分阈值
60 个独立测试案例：提示词冻结后仅用于最终报告
```

若后续训练重排序器或微调模型，应使用按时间窗口和源记录分组的 5 折交叉验证；同一连续异常簇
不能同时出现在训练与测试中。
