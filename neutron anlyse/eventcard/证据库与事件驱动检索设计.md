# 证据库与事件驱动检索设计

本文档定义事件卡之后的下一层：如何把技术资料组织成可定位证据，并由事件卡生成受控检索请求。目标是为预检报告提供可核查的资料依据，而不是让模型根据相似文本自行诊断。

## 1. 这一步解决什么问题

事件卡回答“数据中观察到了什么”；技术资料回答“对这种现象应查阅哪些监测、仪表或数据质量信息”。两者之间不能直接交给 LLM 自由联想，需要建立一条可追溯链：

```text
聚合事件卡
  → 受控检索请求
  → 可定位证据段落
  → 受证据约束的 LLM 预检报告
```

每一条报告说明必须能回指到两类输入：

1. 一个或多个事件卡字段，证明“观察到了什么”；
2. 一个或多个证据段落，说明“为什么建议人工核查该事项”。

这一步不负责判断真实故障，也不允许把检索到的通用资料表述成特定设备的已确认原因。

## 2. 可复用资产与需要替换的部分

仓库已有：

- `corpus/pdf/`：按 IAEA、EPRI/DOE、NRC 等来源分类的技术资料；
- `corpus/md/`：已完整导出的 64 份 Markdown（约 143 MB），并保留标题层级、图像页号和同目录 `_meta.json`；
- `corpus/manifest.jsonl`：现有版本只有 1 条记录，需要从完整 Markdown/PDF 目录重新生成全库清单；
- `code_ref/rag/`：旧的 PDF/Markdown 导出与向量索引代码。

旧方案的“固定字符长度分块 + 单一 embedding 相似度排序”可以复用为**候选证据召回**，但不应再被描述为研究主要贡献，也不能以“自检索准确率”作为主实验。新模块增加的关键内容是：段落定位、事件受控查询、证据筛选和报告引用约束。

## 3. 证据段落，而非匿名文本块

每个可检索单元记为 `evidence_chunk`。它必须是能让人工回到原文复查的段落，不只是向量库中的一串文字。

```json
{
  "evidence_id": "IAEA-OLM-P1-p042-s03-c01",
  "doc_id": "...",
  "source_tier": "core",
  "source_org": "IAEA",
  "document_title": "...",
  "source_path": "corpus/pdf/IAEA/...pdf",
  "page_start": 42,
  "page_end": 42,
  "section_path": ["Chapter 4", "Instrument channel monitoring"],
  "chunk_index_in_section": 1,
  "text": "...",
  "language": "en",
  "topic_tags": ["instrument_channel", "online_monitoring"],
  "content_hash": "..."
}
```

字段含义：

| 字段 | 作用 |
|---|---|
| `evidence_id` | 报告引用和结果复现的稳定标识 |
| `doc_id`、`source_path` | 定位原始文档 |
| `page_start/end`、`section_path` | 让人工直接回到页码和章节 |
| `source_tier`、`source_org` | 支持优先使用权威资料，但不把来源等级当作真值 |
| `topic_tags` | 用于过滤或补充召回，不替代文本检索 |
| `content_hash` | 文档更新后识别段落是否变化 |

### 3.1 切分规则

推荐“**章节/页码优先，长度兜底**”而非纯固定字符切块：

1. 直接读取已导出的 Markdown；同目录 `_meta.json` 提供目录标题对应的页号，原 PDF 保留为最终页码复查来源。Markdown 本身并非每页都有明确边界，因此首版先保存章节定位；仅对需要精确页码的最终引用或提取质量差的文档再读取 PDF；
2. 识别 Markdown 标题，形成 `section_path`；
3. 在同一章节内按自然段合并为段落证据；
4. 只有当段落过长时才按句子边界切分，并保留少量重叠；
5. 表格、图注或提取失败页面标记为特殊类型，不假装为完整正文。

第一版可采用 400–800 个英文词或对应中文字符量作为长度上限，但该长度只是工程参数。证据单元的核心是定位完整、语义边界自然，而不是在大量 chunk-size 网格上寻找一个“最优”数字。

### 3.2 资料范围

先将资料划为三层：

| 层级 | 内容 | 用途 |
|---|---|---|
| Core | IAEA、EPRI/DOE 的在线监测与仪表通道资料 | 优先支撑预检核查建议 |
| Domain | 中子测量、堆芯监测、噪声与仪表资料 | 补充测量对象和现象背景 |
| Supplementary | 其他可类比资料 | 仅在前两层不足时补充，需显式标记 |

这不是判断文献正确性的等级，而是确保报告不会被大量无关资料稀释。

## 4. 事件卡到检索请求的受控映射

检索请求由程序构造，而不是让 LLM 根据事件自由猜测故障原因。

\[
q(e)=O+P(e)+S(e)+T,
\]

其中：

- \(O\)：固定测量对象词，如 `neutron current`、`nuclear instrumentation`；
- \(P(e)\)：由 `event_type` 映射出的观测模式词；
- \(S(e)\)：由 `scope` 映射出的范围词；
- \(T\)：固定预检目的词，如 `online monitoring`、`data quality`、`verification`。

### 4.1 词表 v1

| 事件卡字段 | 受控候选词 | 不应加入查询的词 |
|---|---|---|
| `short_zero` | `brief zero output`, `signal dropout`, `missing signal` | 具体故障名称、真实原因 |
| `sustained_zero` | `sustained zero output`, `signal loss`, `channel availability` | “设备停机”“探测器失效”等结论 |
| `positive_spike` | `positive transient spike`, `signal transient`, `abnormal fluctuation` | “噪声源已确认”等结论 |
| `negative_drop` | `negative transient drop`, `signal transient`, `abnormal fluctuation` | “反应性事故”等结论 |
| `upward_trend` | `sustained rise`, `increasing trend`, `signal drift` | “功率已上升”“反应性变化已确认”等结论 |
| `downward_trend` | `sustained fall`, `decreasing trend`, `signal drift` | “功率已下降”“反应性变化已确认”等结论 |
| `transient_deviation` | `signal transient`, `temporary deviation`, `abnormal fluctuation` | 具体方向、具体故障名称、真实原因 |
| `single_channel` | `single channel`, `channel comparison` | 内部通道编号 |
| `multi_channel_temporal_cluster` | `multiple channels`, `temporal cluster`, `data acquisition` | “共因失效” |

精确时间、原始数值和内部通道名不参与语义查询；它们留在事件卡中供报告事实和人工回查使用。

### 4.2 查询对象

查询模块输出的不是一个裸字符串，而是一条可审计请求：

```json
{
  "query_id": "Q-E001",
  "event_id": "E001",
  "query_text": "neutron current multiple channels positive transient spike online monitoring data quality verification",
  "event_facts": {
    "event_type": "positive_spike",
    "scope": "multi_channel_temporal_cluster",
    "channel_count": 4
  },
  "filters": {"source_tier": ["core", "domain"]},
  "mapping_version": "v1"
}
```

这使得任何检索结果均可回溯到具体事件、具体词表和具体版本。

## 5. 候选召回与证据选择

建议分为三个确定的阶段：

1. **候选召回**：在 Core 和 Domain 文档中，以受控查询召回 top-\(K\) 段落。可采用现代的中英双语检索编码器，模型应作为可配置的底座而非论文创新点。
2. **证据筛选**：保留具有页码和章节定位、且与“观测现象 / 核查目的”直接相关的段落；若只讨论泛泛的核安全背景，则不作为该事件的证据。
3. **证据包生成**：每个事件最多保留有限条证据（例如 3–5 条），并随报告输入提供 `evidence_id`、标题、页码、正文和来源等级。

可选地使用关键词检索与向量检索的并集，再以重排序器或 LLM 进行“是否支撑预检说明”的二分类。无论采用何种模型，最终被引用的证据必须可定位，且筛选决策要保存。

## 6. LLM 输入与输出边界

LLM 的输入只能包含：

- 聚合事件卡中的观察事实；
- 事件卡的来源和限制；
- 固定格式的证据包；
- 明确的禁止项：不能确认机理、不能编造数值、不能把时间共现写成因果。

LLM 输出必须是可解析的结构，并逐项附 `event_id` 和 `evidence_ids`：

```json
{
  "event_id": "E001",
  "observed_facts": ["..."],
  "evidence_based_notes": [
    {"statement": "...", "evidence_ids": ["IAEA-OLM-P1-p042-s03-c01"]}
  ],
  "recommended_checks": [
    {"action": "...", "evidence_ids": ["IAEA-OLM-P1-p042-s03-c01"]}
  ],
  "unconfirmed": ["无法仅依据当前记录确认具体原因。"]
}
```

若没有可支撑证据，模型应输出“资料不足以支持具体说明”，而非补全推理。

## 7. 此阶段应如何评价

这一步不再用“某篇目标文档是否在 top-1”作为主结果，而评估预检证据链是否成立：

| 问题 | 指标 | 标注单位 |
|---|---|---|
| 检索是否提供可用资料 | 证据可用率：top-\(K\) 中至少一条可支撑预检说明的事件比例 | 事件—候选证据包 |
| 引用是否能复查 | 引用可定位率 | 报告引用 |
| 引用是否真正支撑说法 | 证据支撑率（直接支持 / 部分相关 / 不支持） | 报告说法—证据段落对 |
| 无证据时是否克制 | 无证据断言率 | 报告说法 |
| LLM 是否忠实复述事件 | 事件字段忠实率、关键字段遗漏率 | 事件卡—报告对 |

可从 50–100 个事件中抽样建立评价集。先由规则或助手生成候选初标，保留原文定位和理由；最终由人工复核“直接支持 / 不支持”的判定。评价的是文本证据关系和报告边界，不是为数据事件强行标注真实故障。

## 8. 下一步实现顺序

1. 从 `corpus/manifest.jsonl` 建立资料分层清单，并补齐 Core/Domain 标记；
2. 编写 PDF/Markdown 到 `evidence_chunk.jsonl` 的导出器，保存页码、章节和内容哈希；
3. 为事件卡写 `query_builder`，将 v1 词表固化为版本化配置；
4. 接入可配置的候选召回器，先返回证据包而不调用 LLM；
5. 抽样检查若干事件—证据包，修改词表和资料范围；
6. 最后接入 LLM 的结构化报告与自动忠实性检查。

在第 1–4 步完成前，不重新开展旧式 embedding chunk-size / query wording 大规模排名实验，也不把历史“自检索”指标写成新流程的主结果。
